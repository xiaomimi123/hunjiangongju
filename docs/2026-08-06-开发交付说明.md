# 书单号复刻工具 · 本轮开发交付说明

> 面向：项目合伙人 · 撰写日期：2026-08-06
> 覆盖范围：2026-08-04 至 08-06 的三批开发
> 阅读提示：第一、二部分讲「做了什么、能带来什么」，第三部分讲「怎么保证质量」，第四部分是当前状态与后续。

---

## 一、这轮解决的核心问题

我们的产品是**把对标账号的爆款视频，变成可批量复用的模板**，让运营用自己的选题、自己的书单，批量产出「像同一个号」的视频。

复刻精度决定产品价值。上一阶段我们已经能读取剪映工程文件、还原视频的结构与节奏，但实际使用中暴露了三个问题：

| 问题 | 具体表现 | 影响 |
|---|---|---|
| **新版剪映工程打不开** | 上传报错「不是合法文件」 | 2026 年后导出的工程全部无法使用，对标素材来源被卡死 |
| **复刻只到「结构像」** | 节奏、转场对上了，但画面质感、运镜、色调都不像 | 成片一眼能看出不是那个号做的 |
| **生成的画面质量偏低** | 与豆包等消费级 AI 工具的出图有明显差距 | 影响成片的整体观感 |

本轮针对这三点做了三批开发。

## 二、交付的功能

### 批次一：生图质量改造

**问题根因**：原先把口播文案原文直接交给生图模型。但口播文案是「带货话术」（例如"这本书教你走出低谷"），不是画面描述，对生图模型来说是噪音，导致画面平庸、与文案脱节。

**做法**：在生图前加一道「美术指导」环节——由文字模型先把每段口播提炼成一句具体的画面描述（主体、环境、光线），再交给生图模型。

**效果示例**：
- 改造前送给生图模型：`治愈系艺术插画风，一个能烘托这种情绪的安静场景：这本书教你走出低谷…`
- 改造后：`厚涂油画质感，星空下的麦田小路，深蓝与金黄，纯画面不出现文字`

**成本影响**：每次生成多一次文字模型调用，成本可忽略。若文字模型调用失败，自动退回原逻辑，生成不会中断。

**遗留判断**：画面**质感**的上限仍由生图模型决定（当前用阿里百炼 qwen-image）。若仍不满意，可切换到火山豆包 Seedream，改配置即可，不需要改代码。

### 批次二：剪映工程「整包一键导入」

**改造前**：运营要自己在几十个文件里翻出 `draft_content.json` 单独上传，且只导入剪辑参数，配乐和素材要另外手动上传。

**改造后**：页面上点「选择剪映工程文件夹」，系统自动完成全流程：

| 环节 | 系统行为 |
|---|---|
| 找文件 | 自动定位工程主文件；选错文件夹会明确提示 |
| 解析 | 提取剪辑配方，存为可复用框架 |
| 配乐入库 | 工程里的 BGM 自动进 BGM 库，按工程名分文件夹 |
| 素材入库 | 工程里的图片自动进素材库，同样分文件夹 |
| 过滤 | 配音、实拍视频、剪映内部文件自动忽略，不浪费上传流量 |
| 生成联动 | 用这个框架生成时，**自动使用原工程的配乐和素材** |

**业务价值**：运营选中框架 → 直接点生成，出来的就是「原配乐 + 原素材 + 原节奏」的同款。从"导入模板"到"产出成片"中间不再需要手工配置。

**幂等保护**：同一个工程重复导入不会重复入库。

### 批次三：深度拆解（本轮重点，工作量最大）

先解决**新版剪映加密**的问题：2026 年起剪映（含 iOS 19.x）对工程主文件加密。我们发现同一工程内存在一份未加密的等价时间线文件，系统现在会自动回退使用它。**这意味着新导出的对标工程重新可用。**

然后把复刻维度从「结构」推进到「质感」。新增提取并真实作用于出片的参数：

| 维度 | 提取内容 | 实测样例（对标号 @欧子好读） |
|---|---|---|
| **三段结构** | 开场 / 快闪 / 正片的切分与节奏 | 开场 1.5s · 快闪 13 张（每张 100–133ms）· 正片 5 段 |
| **调色** | 滤镜名称与强度、对比度 | 青橙（影视级），强度 0.50，对比度 -0.21 |
| **逐段运镜** | 每个长镜头的运镜方向与幅度 | 推近 / 横移 / 推近 / 推近 |
| **画面缩放** | 构图的松紧程度 | 正片 1.146、快闪 1.053 |
| **转场时长** | 叠化时长 | 467ms |
| **配乐** | 曲目与音量 | 《怎么说我不爱你》，音量 0.44 |
| **水印** | 账号水印，自动填入框架 | @欧子好读 |
| **字幕入场** | 字幕出现方式 | 该工程无字幕，如实标注"未识别到" |

**新增的解析报告**：解析完成后给运营一份人话清单，逐条标注状态：

```
✓ 结构     开场 1.5s · 快闪 13 张 @100–133ms · 正片 5 段（平均 7.2s）
✓ 转场     叠化 467ms
✓ 配乐     《怎么说我不爱你（DJ前奏版）》 音量 0.44
✓ 调色     青橙 强度 0.50 · 对比度 -0.21 · 锐化（无法复刻）
✓ 运镜     4 段有关键帧运镜，按顺序循环套用
✓ 水印     @欧子好读
⚠ 字幕入场  未识别到
✗ 装饰图层／剪映内置商用字体／艺术蒙版——超出模板能力，未复刻
```

**这份报告的设计原则是「不许夸大」**，详见第三部分。

## 三、开发方法：为什么可以相信这些功能是对的

这部分是我认为最值得向合伙人说明的——**功能清单谁都能写，能不能信取决于验证方式**。

### 3.1 流程：设计 → 计划 → 逐任务实现 → 独立评审 → 整批终审

每批开发都走同一条流水线：

1. **设计文档**：先写清楚要做什么、判断依据是什么、明确列出**做不到什么**
2. **实施计划**：拆成 7–9 个独立任务，每个任务写明改哪些文件、测试怎么写
3. **逐任务实现**：每个任务由独立的执行单元完成，**测试先行**（先写会失败的测试，再写实现）
4. **逐任务评审**：每个任务完成后，由**另一个独立单元**审查，它看不到实现过程，只看需求和最终代码
5. **整批终审**：全部完成后再做一次跨任务的整体审查

本轮三批共 **32 次提交**，测试从 372 条增加到 **475 条**，全部通过。

### 3.2 关键做法：拿真实工程对账，而不是只跑测试

**这是本轮最有价值的经验。**

测试用的是我们自己构造的简化数据，而真实的剪映工程总有构造时想不到的结构。所以每个任务完成后，都**强制拿两个真实工程各跑一遍**，把解析结果与人工分析的数值逐项对账。

结果很说明问题：**深度拆解这批 8 个任务里，有 6 个是在这个环节发现问题的，测试本身没抓到。** 举三个例子：

**例一：开场标题认错了。** 测试全绿，但拿真实工程一跑，新模板的开场标题被识别成了「内容来自书评/感悟/素材来源于网络」（那是免责声明）。原因是识别规则用了"位置偏上"当判据，而两个工程的标题一个在上一个在下。改成按"出现时间最早"识别，两个工程都正确。

**例二：一个存在已久的坐标符号错误。** 顺着上面的线索，发现剪映的纵坐标方向在代码里被写反了，导致所有导入框架的字幕位置都跑到画面上方，而书单号的字幕应该在下三分。这个错误此前被当成"对标账号的风格特点"记录在案，实际是 bug。用两个工程的数据加渲染代码的下游公式三方印证后修正。

**例三：缩放数值的口径错误。** 提取出的画面缩放值直接用会导致画面多裁掉约 17%。深入分析发现，剪映的缩放值里**混着"补偿源图片比例差"的成分**，而我们的 AI 生成图本来就是标准比例，不需要补偿。换算成正确口径后，两个不同作者的工程收敛到相近数值，验证了新口径的正确性。

### 3.3 一条硬约束：新功能不许影响现有效果

所有新参数都设计成**可选**，并立下规则：**当框架里没有这些新数据时，生成的视频必须和改动前一模一样**。

这不是靠人工比对保证的，而是用测试锁死。例如运镜的基准缩放参数，默认值取 1.07——这个数**恰好等于**原先写死代码的中点，测试直接断言「传默认值 = 不传参数」，任何一个字符的偏差都会让测试失败。

这条约束在开发过程中真的拦下了一次事故：转场时长接入渲染层时，执行单元写的判断条件会让**所有现有框架**的转场从 720ms 变成 400ms。它在报告里如实写明了这是"有意的行为变更"，我据此发现并要求改正——现在只有真正从工程里提取到转场时长时才覆盖，现有框架输出不变。

### 3.4 诚实原则：宁可说「做不到」，也不假装复刻

这是贯穿本轮的一条准则，具体体现在三处：

**其一，报告不许把默认值当成提取结果。** 当工程里没有某项数据时，解析器会回退到默认值。原先报告会把这个默认值打上「✓」显示成"已识别"——同一屏上方说识别到了，下方警告说没找到。现在改成明确标注「未识别到，用默认值」。

**其二，提取了但渲染不用的参数，必须接上或者标明。** 评审发现两处"提取了却没人用"的参数——界面告诉运营"已提取快闪缩放"，实际渲染根本不读它。这类等于对用户撒谎，一律接入渲染或如实标注。其中转场时长这个参数**是上一阶段就在提取、几个月来一直没接线的**，本轮一并修复。

**其三，无法复刻的能力明确写出来。** 报告里固定有一行：装饰图层、剪映内置商用字体、艺术蒙版——超出模板能力，未复刻。滤镜也如实说明是"近似"而非精确还原（剪映的滤镜是其自有色彩查找表，技术上拿不到）。

还有一个更微妙的例子：字幕入场动画的识别，原本会从水印上的一个**循环装饰动画**推断出"字幕用逐字浮现"。这是巧合而非复刻。改成"入场动画只能从入场动画推断"后，两个样例都诚实返回"识别不出"——看起来像功能没生效，但这才是正确答案。

### 3.5 评审的独立性

评审单元与实现单元完全隔离，只拿到需求文档和最终代码。实践中它确实抓出了实现者自己没意识到的问题，包括：

- 类型定义漏了导出（**当下不报错**，要等下游开发写到一半才撞上，连续两个任务都出现，之后每次评审都专门检查这一类）
- 数值选取依赖了 JSON 里键的排列顺序（当前数据下碰巧正确，但换个工程就会出错）
- 缺少能真正捕获 bug 的回归测试（评审甚至会把代码回滚到修复前，验证新测试确实会失败）

**同样重要的是：评审也会推翻我的判断。** 有一次我预测某个数值应该是 1.107，执行单元算出 1.146 并按要求停下来报告，而不是调整公式去凑我的数字。复核后发现**是我的验证脚本写错了**——如果它当时选择"凑数"，就会把一个正确的实现改坏。

|---|---|---|

三批将一次性部署。本轮改动**不含数据库结构变更**，部署风险低。

### 4.2 待办

**产品侧需要确认的事**：
1. 部署后，用对标工程实测一次完整流程，确认成片观感
2. 生图模型是否切换到火山豆包 Seedream（改配置即可，不需要改代码）
3. 客户的三款字体文件（字由玄真 / 三极极宋 / 莫雪体）——有了才能做到字体同款

**已记录、暂缓处理的技术项**：
- 素材裁剪矩形未计入缩放换算（目前只有一个样例涉及，等更多样本再定）
- 滤镜近似表目前只收录了实测到的「青橙」，随样本积累逐步扩充
- 逐段运镜目前按顺序循环套用，不做与原工程分镜的一一对应（生成视频的分镜数与原工程本就不同）

### 4.3 一句话总结

本轮把复刻能力从**「结构像」推进到「质感像」**，同时解决了新版剪映工程无法导入的卡点。更重要的是，建立了一套**「真实素材对账 + 独立评审 + 不许夸大」**的开发方式——本轮 6 个问题是靠真实工程对账发现的，2 个是靠独立评审发现的，其中还包含一个存在了几个月的老 bug。
